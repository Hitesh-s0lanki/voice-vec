# 09 — v1, and what it measured

Phase A of [08-build-plan.md](08-build-plan.md): a spoken Hindi question reaching a grounded
answer or an honest abstention, end to end, with per-stage timings from the first request.

Everything here is **measured**, not budgeted. Numbers come from `reports/results.json`
(N=300, seed 42) and from the ingest log, and every one is reproducible with the two
commands in [Running it](#running-it).

## The one design decision that overrides 01–08

Those docs assume the pipeline lives in the Next.js app (`src/lib/rag/*.ts`,
`instrumentation.ts`, `@huggingface/transformers`). **It lives in the FastAPI service in
[`src/`](../src/) instead**, and the Next app proxies `/api/ask` to it.

The reason is that the backend already existed, and the Python stack is where the ingest
tooling is — DuckDB over parquet, and `fastembed`, which runs the same ONNX export of the
same model on the same `onnxruntime`. Nothing in the architecture changed: it is still local
embedding, still loopback-or-in-process vector search, still an extractive answer, still
zero network calls after the transcript arrives. The Next-specific advice in 02 and 08
(`instrumentation.ts#register()`, `proxy.ts`, the edge-runtime warnings) maps onto FastAPI's
`lifespan`, which warms the embedder and opens the index before the server accepts traffic.

## What is built

| Piece | Where | State |
| --- | --- | --- |
| Gate 1 — input | [`rag/guardrails.py`](../src/rag/guardrails.py) | length, unsafe denylist, injection strip, language routing |
| Local embedding | [`rag/embed.py`](../src/rag/embed.py) | `multilingual-e5-small`, ONNX, `query:`/`passage:` prefixes applied centrally |
| Vector search | [`rag/store.py`](../src/rag/store.py) | Qdrant, five named-vector slots, **S1 populated** |
| Gate 2 — retrieval | [`rag/guardrails.py`](../src/rag/guardrails.py) | score floor + margin + min-hits |
| Extraction | [`rag/extract.py`](../src/rag/extract.py) | lexical prefilter → embedding rerank → verbatim span |
| Gate 3 — grounding | [`rag/guardrails.py`](../src/rag/guardrails.py) | substring check + citation required |
| Harness | [`rag/harness.py`](../src/rag/harness.py) | timed stages, retries, deadline, trace |
| Analytics | [`services/metrics_service.py`](../src/services/metrics_service.py) | ring buffer, `GET /metrics` |
| UI | [`answer-card.tsx`](../frontend/src/components/answer-card.tsx) | answer, abstention and refusal each render as a real turn |

Not built: S2–S5 and hybrid sparse retrieval, Tier 2 rerank, Tier 3 LLM synthesis with
Gate 4, the Qdrant circuit breaker, E3 answer-quality scoring, and the full-corpus ingest.

## Running it

```bash
uv run python -m scripts.ingest --rows 2000 --recreate   # build the index
uv run python -m src.main                                # serve it
uv run python -m scripts.evaluate --n 300 --seed 42      # reproduce every number below
uv run python -m scripts.demo                            # the guardrail demo
```

Embedded Qdrant is a **single-writer** store: the ingest, the evaluation and the API each
want the same lock, so run them one at a time. `QDRANT_URL` points all of them at a server
instead.

## The index

| | |
| --- | --- |
| rows | 2,000 of `validation/hinval.parquet` |
| passages | 19,987 |
| chunks after dedup | **19,870** (0.6% duplicates) |
| strategy | S1 passage-atomic only |
| tokens per chunk | p50 **91**, p99 **226** |
| chunks at the 512-token cap | 60 (**0.3%**) — truncated, silently |
| build time | **723 s** on the machine below |
| answerable / unanswerable rows | 1,219 / 781 (**39.05%** unanswerable) |

The 39.05% unanswerable share matches the 39.1% [01-dataset.md](01-dataset.md) measured over
the same 2,000 rows, which is a cheap check that the flattening is not dropping labels.

**Dedup was 0.6%, not the "passages repeat a lot" that [03-chunking.md](03-chunking.md)
assumes.** Over 2,000 rows the same passage rarely recurs. The dedup step still earns its
place — it carries the multi-origin provenance the evaluation scorer needs — but it is not
the "cheapest speedup available in the whole ingest" at this scale. Re-measure at 25k rows
before repeating that claim.

## E4 — latency

Requirement 3's window: transcript in, answer out. N=300.

| | P50 | P70 | P95 | P99 | P100 |
| --- | --- | --- | --- | --- | --- |
| **all requests** | **17.0** | 87.0 | 124.6 | 135.8 | **158.6** |
| answered (n=139) | 93.1 | — | 133.9 | — | 158.6 |
| abstained (n=161) | 15.1 | — | 17.8 | — | 24.0 |

**300/300 inside the 200 ms budget**, worst case 158.6 ms — but see
[the caveat below](#the-percentiles-above-describe-a-workload-nobody-runs): this run keeps
the process hot, and interactive use does not.

The headline P50 of 17 ms is not the pipeline being fast — it is the median request
abstaining at Gate 2 and never paying for extraction. Both rows are reported for exactly
that reason. The number to quote for "the system answered a question in under 200 ms" is the
**answered** row: P50 93 ms, P100 159 ms.

Per stage, over the requests that ran each one:

| Stage | P50 | P100 | Budget in [04-latency.md](04-latency.md) |
| --- | --- | --- | --- |
| Gate 1 | 0.12 | 0.32 | 2 ms ✅ |
| Embed | **4.05** | 12.1 | 15–40 ms ✅ *3.7× better* |
| Search | **10.7** | 17.0 | 5–15 ms ✅ |
| Extract | **78.0** | 130.4 | 8 ms ❌ **10× over** |
| Gate 3 | 0.04 | 0.13 | 3 ms ✅ |

**Phase 0a is answered: query embedding is not the risk.** 04-latency called it "the dominant
cost and the main risk" at 15–40 ms; it measures 4 ms, and the whole budget has room because
of it.

### The percentiles above describe a workload nobody runs

The evaluation fires 300 queries back to back, which keeps the ONNX arena and Qdrant's vector
matrix permanently hot. **Interactive voice use is the opposite**: one question, then minutes
of silence. Measured on the same machine, an *answered* query after a 90 s gap:

| | embed | search | extract | total |
| --- | --- | --- | --- | --- |
| after 90 s idle | 45.0 | 38.2 | 116.5 | **200.3** ❌ over budget |
| immediately after | 5.5 | 13.6 | 60.3 | 79.6 ✅ |
| after 90 s idle, **keepalive on** | 9.0 | 15.7 | 66.9 | **92.1** ✅ |

30 s of silence is enough to trigger it, and it does not get worse with longer gaps — the
cost is paging the model arena and the vector matrix back in, not a cache that decays.
Warming once at boot, which is all [04-latency.md](04-latency.md) asks for, only covers the
first request of the process.

So the service runs a **keepalive**: one tiny embed plus a `limit=1` search every
`KEEPALIVE_SECONDS` (default 20), about 12 ms of work per tick. It is disclosed rather than
folded into the headline because it is a mitigation, not an improvement — the underlying
cost is still there, we just stop paying it on the user's request. Set `KEEPALIVE_SECONDS=0`
to measure the difference.

This was caught by looking at a screenshot of the real UI, not by the evaluation harness. A
benchmark that loops is the wrong shape for a workload that idles, and worth fixing in Phase C
by injecting idle gaps into the latency run.

**The risk moved to extraction.** 04-latency budgeted 8 ms for "cosine over sentences already
embedded" — but S1 stores one vector per *passage*, so sentence vectors do not exist at query
time and have to be computed. Embedding is ~5–10 ms per window and **linear in window count;
batching buys nothing**, so the two-pass design (lexical prefilter → embed only the top 6)
is what keeps it affordable. Embedding all ~30 candidate sentences would cost ~200 ms alone.
Indexing S2 sentence-window would remove this stage almost entirely — the vectors would
already be in the index.

## E1 — retrieval

Ground truth `is_selected`, answerable rows only (n=187 of the 300 sampled).

| | recall@1 | recall@5 | recall@10 | MRR@10 |
| --- | --- | --- | --- | --- |
| S1 passage-atomic | 0.369 | **0.722** | 0.797 | 0.510 |

By query type, recall@5:

| Type | n | recall@5 |
| --- | --- | --- |
| DESCRIPTION | 135 | 0.682 |
| NUMERIC | 39 | **0.821** |
| ENTITY | 6 | 1.000 |
| PERSON | 7 | 0.714 |

NUMERIC out-retrieving DESCRIPTION is the opposite of what
[03-chunking.md](03-chunking.md) predicts for passage-atomic chunking, where NUMERIC is
supposed to be S1's weak slice. n=39 is small, and this is recall of the *passage*, not of
the answer span — S2's argument is about extracting the right clause once the passage is
found, which E1 does not test. Worth re-checking at 25k rows before drawing a conclusion.

Two caveats that do not go away with more data: the gold passage is **guaranteed present**
(the corpus was built from these rows), and MS MARCO's passages were themselves retrieved
for these queries, so every candidate is lexically biased toward the query. These are
ranking-against-distractors numbers, not open-domain numbers.

## E2 — abstention, and the honest result

Ground truth `sum(is_selected) == 0`. N=300, of which 113 (37.7%) should abstain.

At the shipped operating point — floor 0.845, margin 0.02:

| | should answer | should abstain |
| --- | --- | --- |
| **answered** | 98 | **41** ← answered the unanswerable |
| **abstained** | 89 | 72 |

```
abstention precision = 0.447      abstention recall = 0.637
answer coverage      = 0.524      F1                = 0.526
```

The sweep, floor held at 0.845 (the floor barely matters — see below):

| margin | precision | recall | coverage | wrong answers |
| --- | --- | --- | --- | --- |
| 0.010 *permissive* | 0.452 | 0.336 | **0.754** | 75 |
| **0.020 balanced — default** | 0.447 | 0.637 | 0.524 | 41 |
| 0.030 *conservative* | 0.436 | **0.903** | 0.294 | 11 |

**Precision sits at ~0.45 wherever the knob is put, against a base rate of 0.377.** Gate 2,
on dense S1-only retrieval, is barely better than a coin weighted by the class ratio. Three
measurements say the same thing:

1. **All three available signals are equally weak.** Ranking answerable above unanswerable:
   top-1 score AUC **0.612**, margin AUC **0.604**, extracted-span cosine AUC **0.615**.
   There is no cheap win by swapping the signal — I checked before accepting the result.
2. **The floor is inert.** F1 is *identical* for every floor from 0.780 to 0.835. e5's cosine
   scores are compressed high (answerable mean 0.894, unanswerable mean 0.884), so almost
   nothing falls below an absolute floor and the margin does all the work.
3. **The margin is degenerate by construction.** Measured over 120 queries, **51% of a
   query's top-10 are its own sibling passages** — MS MARCO retrieved ~10 passages per query
   and we indexed all of them, so the gold passage competes mainly against near-duplicates
   of itself. 24 of 120 queries had ≥8 of 10 slots filled by siblings. A "does the top result
   stand out" test cannot work when the runners-up are the same document by another name.

This is the case [06-guardrails.md](06-guardrails.md) called the hard one — *"it has to
abstain despite finding plausible-looking, on-topic content"* — and the measurement confirms
it is hard rather than assuming it was handled. The fix is not tuning:

- **Sparse/BM25 alongside dense.** Siblings share a topic but not their exact tokens, so
  lexical scoring separates them where cosine cannot. This is the single highest-value item.
- **S2 sentence-window.** "No sentence in the corpus answers this" is a much sharper signal
  than "no passage is about this", and it removes the extraction stage's cost at the same time.
- **Collapsing sibling results before the margin test**, so the margin compares against
  genuinely different documents.

`RETRIEVAL_FLOOR` and `RETRIEVAL_MARGIN` are env-tunable, and the whole sweep is in
`reports/results.json`. **Re-sweep after any re-ingest** — both are index-size dependent.

## What the demo shows

`scripts/demo.py` runs four rows per labelled case rather than one, because a single
hand-picked row is a demo that worked once:

| Case | Result |
| --- | --- |
| answerable · DESCRIPTION | 3/4 answered, with citations |
| answerable · NUMERIC | 2/4 answered |
| unanswerable · labelled | **4/4 abstained** |
| off-topic (gold price today) | abstained |
| unsafe input | **refused at Gate 1 in 0.12 ms**, before anything expensive ran |
| spoken prompt injection | imperative stripped, flagged `injection`, pipeline continued |

The answerable misses are Gate 2 over-refusing, exactly as the 0.524 coverage predicts —
including one case where the labelled gold passage was retrieved at rank 1 and the gate threw
it away.

## Findings that changed the code

**Ingest was 35× slower than it needed to be.** ONNX pads every batch to its longest member,
so a batch of mixed-length chunks charges each short chunk the price of the longest. Sorting
chunks by token length before batching took ingest from ~4 to ~130 chunks/s. It changes
nothing about the vectors.

**A token-length check that could not fail.** The first version counted `len(encoding.ids)`,
but the tokeniser pads a batch out to its longest member — so it reported "p99 512, max 512,
over 512: 0" for a corpus whose real p50 is 91. Counting the attention mask instead is what
produced the real numbers above, and it is what made the length-sorting work at all.

**Indic token inflation is 1.21×, not 1.5–2.5×.** Measured over 19,810 aligned Hindi/English
pairs, excluding pairs at the cap. [03-chunking.md](03-chunking.md) sets chunk sizes assuming
much worse; the e5 sentencepiece vocabulary handles Devanagari better than expected, and the
512-token cap bites 0.3% of chunks rather than a large fraction.

**A payload filter cost 92 ms of the 200 ms budget.** Embedded Qdrant evaluates payload
filters by scanning every point in Python: search took 102 ms with a `language` filter and
10 ms without. The service now applies the filter only when the index holds more than one
language — filtering on the sole indexed value cannot change the result set. A Qdrant server
indexes the field and would not care; the skip is correct in both modes.

**Warming at boot is not enough.** After 30 s idle the next request pays ~60 ms across embed
and search, which took a cold answered query to 200.3 ms — over budget. A 20 s keepalive
brings it to 92 ms. Found by measuring against a screenshot of the real UI rather than the
benchmark loop.

**A deadlock in the store's locking.** `search()` took the access lock and *then* touched the
lazily-built client, whose property took the same non-reentrant lock. The first locked call
hung forever, silently, at 0% CPU. Fixed with a separate connect lock; there is a regression
test that would have caught it.

## What to build next, in order

Ranked by what the measurements say, not by the original plan:

1. **Sparse vectors + RRF fusion.** The abstention gate is the weakest part of v1 and this is
   the most direct fix for it. Also requirement 2's other half.
2. **S2 sentence-window.** Sharpens abstention *and* deletes the 78 ms extraction stage by
   putting sentence vectors in the index.
3. **Re-ingest at 25k rows** and re-sweep. Every threshold here is calibrated against 19,870
   chunks and will move.
4. **S3–S5 and the comparison matrix** — requirement 2's deliverable.
5. **Tier 3 LLM synthesis with Gate 4.** The harness has the stage slot and the timing key;
   nothing else is blocking it.

Deliberately not next: the Qdrant circuit breaker (nothing to trip it in embedded mode) and
int8 quantisation (search is 10 ms, well inside budget).

## Known limitations

- One language, one strategy, 2,000 rows of a 98k-row split.
- Gold-in-corpus and MS MARCO lexical bias make E1 optimistic (see E1 above).
- Latency is in-process and sequential; concurrent load is unmeasured.
- Gate 1's unsafe denylist is a handful of patterns; its false-positive rate on legitimate
  queries is **not yet measured**, which [06-guardrails.md](06-guardrails.md) asks for.
- E3 (answer quality against gold `Answer`) is not implemented, so "the answers are good" is
  currently unevidenced — only "the answers are grounded", which Gate 3 guarantees structurally.
- P100 over N=300 is a single sample and is not comparable to P100 at another N.
